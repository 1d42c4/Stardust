01 /

Different bits become 1.

XOR means exclusive OR. Matching bits produce 0; different bits produce 1. Astra combines byte zero of FILE_A with byte zero of key.key, and continues in order.

For example, FF 0F AA XOR 0F 0F 55 produces F0 00 FF. Each pair of hex digits represents one byte.

Enter 00–FF. This example runs in your browser and does not read any files.

XOR is reversible: (A ⊕ key) ⊕ key = A. Use exactly the same key bytes to restore a file. Key length alone does not make XOR secure encryption: this tool does not generate random keys, prevent key reuse, or authenticate data.

02 /

Build once. Keep the files together.

Requires Rust 1.88 or newer and Cargo. Run the build commands from this project's directory. There are no third-party crates; builds and tests work offline once the Rust toolchain and platform linker are installed.

Windows · PowerShell

cargo build --release --offline --locked
Copy-Item .\target\release\astra-xor.exe .\astra-xor.exe
# Put a.bin and key.key beside astra-xor.exe.
.\astra-xor.exe a.bin out.bin

Build output: target\release\astra-xor.exe. Use the Windows MSVC toolchain with its C++ build tools and Windows SDK.

Linux · shell

cargo build --release --offline --locked
cp target/release/astra-xor ./astra-xor
# Put a.bin and key.key beside astra-xor.
./astra-xor a.bin out.bin

Build output: target/release/astra-xor. Install a C linker, such as the one supplied by your distribution's build tools.

You can copy the executable to any writable working folder. The folder should look like this before a run:

your-folder/
  astra-xor.exe     (Windows) or astra-xor (Linux)
  a.bin            (your input; choose its filename)
  key.key          (required name; at least as many bytes as a.bin)
  out.bin          (created or replaced after success)

The executable's directory controls file lookup. Launching C:\tools\astra-xor.exe a.bin out.bin from another folder still reads C:\tools\a.bin and C:\tools\key.key, and writes C:\tools\out.bin. Linux behaves the same way.

When using cargo run --release -- a.bin out.bin, place the data and key in target/release. If you use cargo install --path . --locked, the files belong beside the installed executable. A copied executable in a dedicated data folder is usually easier to manage.

03 /

The key must cover the whole input.

astra-xor [--] <FILE_A> <OUTPUT>
astra-xor --in-place [--] <FILE_A>

Supply two filenames to save to a separate output, or --in-place and one filename to replace FILE_A. Paths are not accepted. The second input (B) is always key.key; do not pass it as an argument. Before creating a temporary file or modifying output, Astra checks both inputs and their lengths.

Atomic in-place replacement: astra-xor --in-place a.bin writes the complete result to a temporary file beside a.bin, syncs it, then replaces that filename. It needs free disk space for the complete result. FILE_A must be writable and cannot be the key, executable, or a hard link to either. Running the command again with the same key restores the original bytes.

Filename rules on both systems

Spaces, Unicode, leading dots, and native OS filenames are supported. Quote names containing spaces. Use -- before filenames starting with a dash. A lone - is an ordinary filename, not standard input.

Absolute paths, subdirectories, ./, ../, both slash styles, Windows drive prefixes and alternate data streams are rejected. Both systems also reject control characters, < > : " | ? *, trailing dots/spaces, Windows device names such as NUL or COM1, and the reserved .astra-xor- prefix.

Name the key key.key exactly, and use the actual case of input names. Windows normally ignores case; Linux normally distinguishes it. Astra checks file identity when protecting inputs. Without --in-place, a case alias or hard link to either input cannot be used as output. The key and executable remain protected in both modes.

Moving from version 0.2

The old three-filename command and the --repeat/--truncate options have been removed. Rename your B file to key.key, make sure it is long enough, put the files beside the executable, and use astra-xor a.bin out.bin. No bytes from FILE_A are discarded and the key never cycles.

04 /

Finish the result before replacing a file.

  1. Resolve the executable and validate the files.

    Use the canonical executable directory, independent of the shell's working directory. Require regular input files and a sufficiently long key. Protect the key and executable, including hard links. Only explicit --in-place allows replacing FILE_A; verify that its path still names the opened input before transforming it.

  2. Write a separate temporary file in the same folder.

    Create it exclusively. Two 64 KiB buffers keep processing memory bounded, regardless of file or key size. Short and interrupted reads/writes are handled; a read error or a key becoming too short fails the run.

  3. Check, sync, then rename.

    Detect input growth and observed length, permission, or modification-time changes, plus Unix status-change times. Sync the completed temporary file, recheck the destination's identity and metadata, and rename the result into place. On Linux, also sync the parent directory. Never delete the old output first.

Existing unrelated output is replaced without a prompt after success. Keep enough free space for the complete result while the old output still exists. The executable's folder must allow creating and renaming files. Read-only or locked output fails safely.

Links, special files, and permissions

Input, key, and output file symlinks are refused, including links to the same folder and dangling links. Windows reparse points (including cloud placeholders) are also refused; use ordinary local copies. Directories, devices, and pipes are not supported.

Hard-linked inputs are regular files and can be read. A separate output may not be a hard link to either input or the executable. In-place replacement changes the directory entry, not the original file object: other hard links and already-open readers keep the original bytes. Readers opening the filename after replacement see the complete result. Windows readers must permit deletion/renaming; otherwise replacement fails safely.

New Unix outputs use mode 0600, subject to the process's umask. Replacement preserves ordinary Unix access bits, without setuid/setgid/sticky bits. Ownership, ACLs, timestamps, and other metadata are not guaranteed to survive replacement. On Windows, input handles permit other readers but prevent concurrent writes or deletion while open. An existing output also refuses active writers and prevents new writers through processing, file sync, and the final rename. In-place replacement keeps that protection after its input reader closes.

File identities use Unix device/inode pairs and Windows volume/128-bit file IDs. If file identity cannot be obtained, Astra exits before writing. See Windows file identity, Unix metadata, and Windows filename rules.

Failures, concurrent changes, and interrupted runs

Failures before publication clean up the temporary file without deleting the destination, including FILE_A in in-place mode. If Linux directory syncing fails after the rename, the completed output is already in place; Astra returns a failure and explicitly reports that publication succeeded but durability is uncertain. Do not blindly retry that error in in-place mode: XORing again would undo the completed transformation. Forced termination or filesystem failures can leave a .astra-xor-*.tmp file. Remove such files only after confirming no Astra process is still using them.

Keep inputs, executable, and directory entries stable during a run. Metadata checks catch observable changes but are not a snapshot or a defense against hostile concurrent directory manipulation. Do not direct simultaneous runs to the same output filename.

Linux checks directory-sync support before writing and syncs that directory again after publishing the completed file, following the Linux fsync requirements. Filesystems that cannot sync directories fail before replacement. Windows syncs file contents before renaming, but does not guarantee that the renamed directory entry survives power loss. Physical disk failure, filesystem corruption, unusual network filesystems, and abrupt termination cannot be made failure-proof by this program. See Rust's file sync, rename, and executable path documentation.

05 /

A few useful commands.

The commands below assume Astra is on PATH. Otherwise use .\astra-xor.exe on Windows or ./astra-xor on Linux. Every named file still belongs beside that executable.

Process a file

astra-xor a.bin out.bin

Automatically reads key.key. A short or missing key fails before writing.

Mask, then restore

astra-xor message.txt masked.bin
astra-xor masked.bin restored.txt

Keep key.key unchanged for both commands. This demonstrates XOR's reversibility.

Replace a file in place

astra-xor --in-place message.txt
# Run the same command again to restore its bytes.
astra-xor --in-place -- -input.bin

The original remains intact until the completed result replaces its filename. Use -- before a filename starting with a dash.

Names with spaces or dashes

astra-xor "input one.bin" "output file.bin"
astra-xor -- -input.bin -output.bin

Names only: even ./input.bin is rejected.

Help and version

astra-xor --help
astra-xor --version

Also accepts -h and -V. These informational commands do not require input files or a key.

Exit codeMeaning
0Success, help, or version. A successful data run prints its byte count.
1Runtime failure: missing/short key, missing input, unsafe destination, changed input, or I/O error. A diagnostic goes to standard error.
2Invalid arguments: wrong filename count, unknown/removed option, or rejected filename/path.

Local validation, October 26, 2026: all 139 Windows tests and all 141 Linux tests passed in both debug and release with Rust 1.99.1 and Rust 1.88.0. Formatting with stable Rust, Clippy with warnings denied on both toolchains, and release builds also passed. Linux ran directly in Ubuntu WSL2 on its native filesystem. Results are saved in target/validation/windows.log and target/validation/linux.log; all 14 recorded manifest, lockfile, source, and test hashes in each log match the checked files. The CI workflow checks the same Windows/Linux and Rust-version matrix; remote CI execution was not run in this local review.

Reliability fix: Windows output inspection previously allowed concurrent writers, and in-place replacement released its write protection before syncing. Windows can defer last-write timestamp updates until writer handles close, so metadata checks alone cannot reliably detect those edits. Output inspection now holds a reader that denies write sharing through the rename. Regression tests verify early refusal of an active writer, protection during processing and sync, and successful replacement after a writer closes. Unix retains its metadata-change tests.

Run Linux checks in Ubuntu WSL

From this project's directory in Linux, run bash scripts/test-linux.sh. The runner checks stable Rust and Rust 1.88.0 and saves target/validation/linux.log. It snapshots the source, builds and tests under Linux's /tmp, sets a predictable test umask, and limits each Cargo build/lint/test command to five minutes. This keeps Linux permissions and symlink tests off Windows-mounted filesystems and separates Windows and Linux build outputs.

On a fresh Ubuntu install, add --install-tools to install missing C build tools and Rust toolchains using Rust's official installer. If sudo requests a password, enter it in your terminal; the script does not store credentials. After setup, Cargo builds and tests run offline.

From PowerShell, replace the example project path below with your own WSL path:

wsl -d Ubuntu -- bash /mnt/c/path/to/astra-xor/scripts/test-linux.sh --install-tools

Limits of the tests

Fault injection covers read/write failures, cleanup, a file-sync failure before publication, and a directory-sync failure after publication. Windows tests exercise actual failed renames and sharing restrictions. The suite does not simulate physical power loss, arbitrary filesystem corruption, hostile directory races, every filesystem implementation, or every possible failure of a disk-sync operation. Passing tests support the stated behavior; they cannot promise failure-proof storage.
