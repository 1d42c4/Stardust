01 / Get started

Build & run

VersaKey deterministically creates key.key in the current working directory. To reproduce a file, use the same password, byte count, generator suite, and compatibility-critical configuration.

1. Build the executable

Use a terminal on Windows or Linux with Rust and Cargo installed. The project pins Rust 1.98.1 in rust-toolchain.toml, including rustfmt and clippy. From the project directory, run:

cargo build --release --locked

Build separately on each operating system. Use a release build, especially for large files.

2. Choose a generator

For the original Argon2id + AES-256-CTR suite, run the compiled executable:

# Windows PowerShell
.\target\release\versakey.exe argon2-aes

# Linux
./target/release/versakey argon2-aes

Alternatively, build and run through Cargo:

cargo run --release -- argon2-aes

3. Enter the size and password

Enter a decimal byte count, then enter the same password twice at the hidden prompts. For example, 1048576 creates a 1 MiB file.

Each successful run replaces key.key. All five suites use the same filename in the current directory. Move or rename an existing key before generating another if you need to keep both.

Interactive usage

The subcommand is required; there is no implicit default generator. The size and password are entered interactively. Passwords are never accepted as command-line arguments.

  1. Start VersaKey with one of the five subcommands.
  2. At Key size in bytes:, enter a whole number from 1 to 20000000000, inclusive. Use digits only, with no commas or unit suffix.
  3. At Password: and Confirm password:, enter a nonempty, matching password. Input is hidden.
  4. Wait for Created key.key (<size> bytes).

The maximum is 20,000,000,000 bytes: 20 decimal GB, approximately 18.63 GiB. Memory use stays bounded by the stream buffer and the selected key derivation function’s fixed working set.

Help and version

Use the executable path shown above, or versakey if it is on your PATH:

versakey --help
versakey scrypt-aes --help
versakey --version

A missing or unknown subcommand, or any unexpected argument, fails before a password prompt or file write.

Choose a generator suite

Each suite derives a 32-byte key from the password, then expands it into the requested output. A key derivation function (KDF) makes password guessing more costly.

Run any suite through Cargo

Choose one command per generation:

cargo run --release -- argon2-aes
cargo run --release -- scrypt-aes
cargo run --release -- pbkdf2-aes
cargo run --release -- argon2-chacha20
cargo run --release -- argon2-blake3

Record the subcommand and exact byte count. The suites are deliberately domain-separated and non-interchangeable. They produce different bytes for the same password and size, and key.key contains no suite header.

Output handling

Generation streams through a 1 MiB buffer. Memory use does not grow with the requested file size; it is bounded by the buffer plus the chosen KDF’s fixed working set.

VersaKey writes to a temporary file, flushes and synchronizes it, then atomically replaces key.key. A derivation or write failure before the final replacement preserves an earlier key file.

Interrupted generation

Normal errors and Rust unwinding remove the temporary file. A forced process kill, abort, or power loss can leave a partial .key.key.* file. After confirming that no VersaKey process is running, you can remove that stale file. Stale files are not removed automatically because another concurrent VersaKey process may still own them.

Platform behavior

  • Unix: the containing directory is synchronized after replacement. A rare failure at that point is reported as already committed; the replacement cannot be rolled back.
  • Windows: the completed temporary file is synchronized before replacement, but the same directory-sync path is unavailable. A sudden power loss immediately after replacement can have weaker rename-durability guarantees.
  • Windows permissions: the replacement inherits the containing directory’s access-control policy instead of preserving a custom ACL on the old key.key. Use a suitably restricted directory for sensitive output.

Determinism & security

What makes a file reproducible

The password, requested byte length, suite domain, application salt and pepper, KDF parameters, and stream construction determine the output. Changing the requested size changes the entire output rather than retaining the shorter file’s stream prefix.

Password strength sets the limit

Output entropy is limited by the password-derived 256-bit key. A large file is deterministic pseudorandom material; its size does not make it a true-random one-time pad.

Anyone who obtains key.key can test password guesses offline by regenerating it. Argon2id and scrypt raise guessing costs through memory-hard work, but no KDF adds entropy to a weak password. Use a long, high-entropy passphrase.

PBKDF2 is CPU-hard but not memory-hard. Its low memory use and broad standardization can suit constrained or compatibility-oriented deployments, while also allowing more economical parallel guessing than the configured Argon2id or scrypt suites. Prefer a memory-hard suite unless you need that tradeoff.

Repeating bytes and stream behavior

Individual bytes and short substrings can repeat in random-looking output. No generator can make every byte unique after 256 bytes. These suites do not cycle or copy a shorter digest.

The AES-256-CTR suites maintain one stream without reusing its 128-bit counter within a generated file. Because AES is a permutation, their aligned 16-byte blocks cannot repeat at the supported sizes. That specific guarantee does not apply to ChaCha20 or BLAKE3 output.

Pepper and memory cleanup

The compiled-in pepper can be extracted from the executable. It diversifies builds but does not replace a strong password or an external secret.

VersaKey zeroizes the password values and key/buffer state it owns. The third-party scrypt and PBKDF2 implementations do not guarantee erasure of every internal intermediate allocation after derivation.

Compatibility with earlier executables

The five generators now live in one executable. Each subcommand retains its predecessor’s application salt, pepper, domain, KDF parameters, and stream construction, preserving the original output for existing password-and-size combinations.

Tests & development checks

Run the complete test suite in release mode using production-strength KDFs:

cargo test --release --locked
cargo fmt --all -- --check
cargo clippy --all-targets --locked -- -D warnings

Per-suite tests cover original known-answer output, fixed configuration, repeated small and large generations in separate directories, password and size sensitivity, exact file lengths, and failed replacements.

A 2 MiB + 137 byte fixture crosses two production buffer boundaries. Its entire content is compared with direct AES counter encryption, one ChaCha20 expansion, or one BLAKE3 XOF read. Tests reject repeating whole-file periods from 1 byte through 1 MiB and check for duplicate aligned 16-byte blocks in that fixture.

These are regression checks for accidental repetition and stream resets, not proof that all output lacks repeated substrings or exhaustive coverage of every supported size.

Shared reliability checks cover partial and interrupted writes, write-zero errors, injected disk failures around buffer boundaries, preservation of an existing key before commit, temporary-file cleanup on errors and unwinding, counter limits, bounded writes, hidden-password handling, and Unix permissions.

Successful CLI tests use the real parser, dispatch, derivation, and writer with an injected password reader. Subprocess tests cover help, argument validation, suite selection, and invalid size handling. All subcommands use the shared implementations for their selected algorithms, KDF costs, zeroization, and atomic replacement.

Linux and WSL checks

# Linux, from the project directory
bash scripts/test-linux.sh

# Windows PowerShell, with Ubuntu installed in WSL
wsl.exe -d Ubuntu -- bash scripts/test-linux.sh

The script runs formatting, tests, lint, and a release build. By default it uses target/linux to separate Linux artifacts from native Windows builds; an existing CARGO_TARGET_DIR overrides that location.

Troubleshooting

“A generator subcommand is required”

Supply a suite, such as argon2-aes. Use versakey --help to list all choices. With Cargo, put the subcommand after --.

The size is rejected

Enter digits only, between 1 and 20000000000. For example, use 1048576 instead of 1 MiB, 1,048,576, or 1e6.

The password is blank or the two entries differ

Run the command again and enter the same nonempty password at both prompts. Hidden input does not display the password as you type.

A file operation fails

Check write access and available disk space in the current directory. The temporary file must fit alongside any existing key.key until replacement completes.

The error says the key was already created or replaced

A directory-sync failure after replacement, or a console error while reporting success, can occur after the output is committed. Read the error carefully: it does not mean the earlier key was preserved.

A regenerated key is different

Check the exact password, byte count, suite, and build configuration. Matching only the password is insufficient; the output file has no suite header to recover the original choice.
